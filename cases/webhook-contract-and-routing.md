# 웹훅의 전송 형식과 목적지를 분리 검증한다

## 맥락

외부 웹훅을 통해 이벤트를 전달하는데, HTTP 호출 자체는 단순해 보여도 대상 서비스가 기대하는 본문 형식과 목적지 오버라이드의 권한·존재 조건이 불명확한 경우다.

## 불변조건

- 전송 성공은 클라이언트의 요청 발행이 아니라 대상 서비스의 수신 기준으로 판단한다.
- 본문 형식과 목적지 지정은 독립된 계약으로 검증한다.
- 기본 목적지로 충분한 경우에는 가변 목적지 오버라이드를 보내지 않아 실패 조건을 늘리지 않는다.

## 문제와 재현

같은 웹훅 URL이라도 JSON 본문, form payload, 목적지 지정 여부에 따라 결과가 달라질 수 있다. 단순 HTTP 상태나 내부 로그만 보고 성공으로 판단하면, 실제 메시지가 도착하지 않거나 권한 없는 목적지 지정 때문에 실패한 사실을 놓친다.

## 대안과 결정

사용자별·상황별 다중 목적지 라우팅이 필수라면 목적지 필드를 유지하고 허용 목록, 권한 검증, 실패 관측을 설계한다. 그 요구가 없다면 웹훅 생성 시 정한 기본 목적지를 사용하고, 호출부에서 목적지를 재지정하지 않는다.

전송 형식은 대상 서비스 문서와 실제 수신으로 확인한다. 단위 테스트는 요청의 Content-Type과 본문에 금지된 목적지 필드가 없는지를 고정해 회귀를 막는다.

## 검증

- 각 후보 본문 형식으로 실제 수신 여부를 한 번 확인한다.
- 목적지 오버라이드 유무를 분리해 실패 조건을 확인한다.
- 전송 코드가 요구한 Content-Type과 payload 구조를 만드는지 테스트한다.
- 실패 로그가 URL·토큰 등 민감한 전달 정보를 남기지 않는지 확인한다.

## 적용 범위와 비적용 조건

- 적용: 채팅, 자동화, 배포 알림처럼 외부 웹훅의 수신 결과가 운영 흐름에 중요한 연동.
- 비적용: 목적지가 고정된 내부 메시지 브로커처럼 호출자에게 목적지 지정 권한이 없는 경우. 이때도 payload 계약 검증은 필요할 수 있다.

## 다음에 확인할 질문

- 대상 서비스가 요구하는 Content-Type과 본문 형식은 무엇인가?
- 목적지 오버라이드는 실제 요구사항인가, 기본 목적지로 충분한가?
- 테스트는 HTTP 응답뿐 아니라 실제 수신과 민감정보 비노출을 확인하는가?
