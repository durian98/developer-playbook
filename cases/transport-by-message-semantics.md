# 전송 채널은 기술 이름보다 메시지의 실패 조건으로 나눈다

## 맥락

제어 명령, 실시간 관제 알림, 연속 영상, 영속 이력을 하나의 실시간 채널에 넣으면 구현은 한곳에 모이지만 데이터 크기와 복구 요구가 다른 흐름이 같은 버퍼와 연결을 경쟁한다.

## 불변조건

- 대용량 연속 데이터의 적체가 경보와 제어 메시지를 고갈시키지 않는다.
- 연결이 끊겨도 영속 이력은 다시 조회할 수 있다.
- 각 채널의 인증, 재연결, 순서, 중복 처리 계약을 설명할 수 있다.
- 실시간 전달 여부와 데이터 보존 여부를 같은 의미로 사용하지 않는다.

## 대안과 결정

하나의 WebSocket은 연결 관리가 단순하지만 큰 payload와 중요 제어가 같은 송신 버퍼와 장애 범위를 공유한다. 반대로 모든 흐름을 분리하면 계약과 운영 지점이 늘어난다.

메시지 성격에 따라 장치 이벤트·제어는 양방향 WebSocket, 화면 구독 메시지는 메시징 프로토콜, 연속 영상은 영상 전송 경로, 이력·설정은 요청·응답 API로 분리했다. 영상이 메시징 채널에서 빠진 뒤에는 남은 메시지 크기에 맞게 버퍼도 줄였다.

핵심은 특정 프로토콜 조합을 복사하는 것이 아니라 처리량, 지연, 유실 허용, 재조회 가능성, 소비자 수가 다른 데이터를 같은 실패 경계에 두지 않는 것이다.

## 확인한 범위와 남은 검증

- 영상 전송 경로 변경과 네트워크 송신량 변화를 확인했다.
- 각 메시지 경로의 코드와 버퍼 설정을 확인했다.
- 느린 구독자, 재연결 폭주, 중복 구독을 포함한 장시간 부하 결과는 확인하지 못했다.

## 적용 범위와 비적용 조건

- 적용: 제어·알림·미디어·이력이 함께 존재하는 관제, 로봇, IoT 시스템.
- 비적용: 데이터 크기와 복구 요구가 유사하고 트래픽이 작은 단일 기능. 분리 비용이 장애 격리 이점보다 클 수 있다.

## 다음에 확인할 질문

- 각 메시지는 유실돼도 되는가, 다시 조회할 수 있는가?
- 큰 payload가 중요한 작은 메시지와 같은 버퍼를 사용하는가?
- 채널마다 인증과 재연결 정책이 일관되게 관리되는가?
- 느린 소비자 하나가 다른 소비자나 생산자에게 어떤 영향을 주는가?
