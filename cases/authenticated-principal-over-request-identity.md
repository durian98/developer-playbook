# 요청 본문의 사용자 ID 대신 인증 주체를 신뢰한다

## 맥락

행동·분석 이벤트처럼 요청에 사용자 식별자가 함께 들어오고, 그 값이 개인화나 권한 판단에 사용되는 API다. 요청 본문의 ID는 라우팅에 필요한 힌트일 수 있지만 인증된 사람이라는 증거는 아니다.

## 불변조건

- 저장할 사용자 주체는 인증 컨텍스트에서 결정한다.
- 본문에 ID가 없으면 인증 주체를 사용한다.
- 본문에 ID가 있으면 인증 주체와 일치하는지 확인하고, 다르면 저장하지 않는다.
- 조용히 다른 ID를 덮어써서 클라이언트 버그와 공격 시도를 숨기지 않는다.

## 문제와 재현

인증은 되어 있지만 서비스가 본문의 `userId`를 그대로 저장하면 누구나 다른 사용자 이름으로 이벤트를 쓸 수 있다. 이벤트가 추천·분석 입력으로 들어가면 접근 우회뿐 아니라 다른 사람의 결과를 오염시키는 데이터 무결성 문제가 된다.

로그인한 사용자 A의 token으로 사용자 B의 ID를 보낸 뒤 저장된 주체를 확인하면 재현할 수 있다. 인증 헤더가 없거나 유효하지 않은 요청도 별도로 거부해야 한다.

## 대안과 결정

본문 ID를 정본으로 삼는 방식은 클라이언트가 주체를 선택하게 만든다. 반대로 본문 ID를 항상 버리고 인증 주체로 덮어쓰면 잘못된 클라이언트가 계속 202를 받아 계약 오류가 숨겨진다.

인증 주체를 정본으로 두고, 본문 값이 있으면 일치 여부를 검증한다. 불일치는 명시적인 403으로 거부해 데이터 오염과 클라이언트 버그를 모두 드러낸다. 서버 내부 작업은 사용자 요청과 다른 별도의 producer·권한 경로로 표현한다.

## 검증

- 본문 ID가 없는 정상 요청이 인증 주체로 저장되는지 확인한다.
- 본문 ID가 인증 주체와 다르면 저장·후속 이벤트 없이 거부되는지 확인한다.
- 다른 사용자의 ID를 반복해도 성공 응답이나 개인화 입력이 생기지 않는지 확인한다.
- 인증 주체가 없는 요청은 인증 실패로, 잘못된 주체는 주체 불일치로 구분한다.
- 서버가 생성한 이벤트는 클라이언트 본문과 구별되는 producer와 트랜잭션 경계를 갖는지 확인한다.

실제 API에서 본문 ID가 인증 주체와 다를 때 403으로 거부하고, 없을 때 인증 주체를 사용하도록 구현했다. 기존에는 임의의 사용자 ID가 저장될 수 있었고 개인화 입력을 오염시킬 수 있었으며, 회귀 테스트로 두 방향을 고정했다.

## 적용 범위와 비적용 조건

- 적용: 사용자 ID가 요청 본문에 포함될 수 있는 이벤트·리액션·활동 기록 API.
- 비적용: 로그인 전 익명 이벤트. 이때도 임의의 고정 사용자 ID를 쓰지 말고 이벤트 또는 aggregate 단위의 익명 주체를 정의한다.
- 관리자가 다른 사용자를 대신해 기록하는 기능은 일반 사용자 API와 분리하고, 별도의 명시적 권한·감사 계약으로 다룬다.
