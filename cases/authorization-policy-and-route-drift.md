# 보안 정책과 실제 라우트는 양방향 계약으로 검사한다

## 맥락

컨트롤러 매핑과 인증 허용 목록이 서로 다른 파일에 있고, 여러 작업이 각각을 수정하는 웹 애플리케이션이다. 두 변경이 서로 다른 줄에 있으면 Git 충돌은 없지만, 최종 조합은 기능을 막거나 인증 없이 새 경로를 열 수 있다.

## 불변조건

- 모든 엔드포인트는 의도한 인증·인가 정책을 하나씩 가진다.
- 허용 목록에는 실제로 존재하는 고정 경로만 남긴다.
- 로그인 전에 호출되는 경로가 허용 목록에서 빠지면 테스트가 실패한다.
- 경로 검색이나 패턴 파싱이 아무것도 찾지 못해도 초록이 되지 않는다.

## 문제와 재현

허용 목록에서 실제 컨트롤러가 없는 경로를 찾는 검사만 있으면 미래의 과도한 공개는 잡을 수 있다. 하지만 컨트롤러 경로가 목록에서 빠진 현재의 기능 장애는 잡지 못한다.

실제 병합에서는 한 변경이 로그인 챌린지 매핑을 되살리고 다른 변경이 “그 매핑이 없다”고 판단해 허용 목록에서 지웠다. 두 변경은 충돌 없이 합쳐졌고, 경로는 존재하지만 인증이 필요한 상태가 되어 로그인 첫 요청이 401로 막혔다. 또 조건부 profile을 평가하는 스캐너는 테스트에서 경로를 0개 찾고도 성공을 반환할 수 있었다.

## 대안과 결정

사람이 보안 설정과 컨트롤러를 매번 대조하는 방식은 일회성 발견에는 유효하지만 회귀를 막지 못한다. 허용 목록만 검사하면 한 방향의 누락을 놓치고, 애플리케이션을 전체 기동해 확인하면 profile·외부 의존성 때문에 경로 자체를 안정적으로 열거하기 어렵다.

라우트를 정책 표에 등록하고, 다음 두 방향을 모두 검사한다.

- 정책 표에 있지만 실제 경로가 없는 고정 허용 목록은 실패한다.
- 로그인 전에 필요한 실제 경로가 허용 목록에서 닫혀 있으면 실패한다.

와일드카드는 “경로 변수 자리”가 아니라 구현한 패턴의 의미대로 해석한다. 경로를 하나도 찾지 못하면 성공이 아니라 실패로 처리하고, 반드시 있어야 하는 경로의 하한도 둔다. 이 검사는 정책이 업무적으로 옳은지 대신, 정책과 구현이 서로 빠지지 않았는지를 재는 장치다.

## 검증

- 실제 컨트롤러 경로와 정책 표의 차이를 양방향으로 비교한다.
- 고정 허용 경로가 모두 실제 매핑으로 이어지는지 확인한다.
- 로그인 전 경로를 닫았을 때 첫 요청이 401이 되는 회귀 테스트를 확인한다.
- 스캐너가 profile 조건으로 0개를 반환해도 실패하는지 확인한다.
- 새 endpoint를 추가할 때 정책 표와 해당 인가 테스트가 함께 바뀌는지 diff로 확인한다.

경로 열거·허용 목록 대조·로그인 전 경로 개방을 별도 테스트로 두었고, 매핑과 허용 목록이 서로 어긋나는 두 방향을 모두 검사하도록 확인했다. 이 검증은 허용 목록의 누락을 다루며, 리소스 소유자 판정 같은 업무 인가의 정확성은 별도 통합 테스트가 필요하다.

## 적용 범위와 비적용 조건

- 적용: 인증 필터, 보안 허용 목록, 컨트롤러 라우트가 분리된 웹 애플리케이션.
- 비적용: 단일 선언에서 라우트와 정책이 함께 생성되어 drift가 구조적으로 불가능한 프레임워크. 그래도 정책 의미를 검증하는 테스트는 필요하다.

- 경로를 찾지 못한 테스트가 정말 “없음”을 의미하는가, 아니면 스캐너가 조건에서 걸러진 것인가?
