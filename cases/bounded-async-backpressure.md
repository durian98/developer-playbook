# 비동기 처리는 큐의 상한과 포화 동작까지 함께 결정한다

## 맥락

네트워크 수신 스레드에서 데이터베이스 쓰기와 외부 부수 효과를 모두 수행하면 저장 지연이 다른 메시지 수신까지 막을 수 있다. 작업을 executor로 넘기면 정상 부하의 결합은 줄지만, 처리량보다 입력이 빠를 때 어디에 적체할지가 새로운 문제가 된다.

## 불변조건

- 정상 부하에서는 느린 저장 작업이 수신 루프를 직접 점유하지 않는다.
- 입력 폭주가 메모리의 무제한 증가로 이어지지 않는다.
- 중요 이벤트는 큐 포화 시 조용히 폐기되지 않는다.
- 순서가 중요한 작업은 병렬화 때문에 의미가 바뀌지 않는다.

## 대안과 결정

무제한 큐는 순간 지연을 감추지만 메모리 고갈과 오래된 작업 누적을 만든다. 여러 worker는 처리량을 높일 수 있지만 순서와 동일 키 경쟁을 다시 설계해야 한다. discard 정책은 수신 스레드를 보호하지만 유실을 제품 동작으로 받아들일 수 있을 때만 적합하다.

순서를 보존해야 하는 중요 이벤트에는 단일 worker와 bounded queue를 사용하고, 포화 시 호출 스레드가 작업을 수행하도록 역압을 전달했다. 이 선택은 유실 대신 수신 지연을 감수한다. 따라서 비동기화가 병목을 제거했다고 표현하지 않고, 병목이 드러나는 위치와 실패 방식을 통제한 것으로 본다.

## 확인한 범위와 남은 검증

- 전용 executor, 단일 worker, bounded queue, 포화 정책이 실제 처리 경로에 연결된 것을 확인했다.
- 기능 경로와 처리 순서는 확인했지만 burst·soak 부하 시험은 수행되지 않았다.
- queue depth, 처리 지연 p95/p99, 호출 스레드 전환 횟수, 연결 회복 시간은 추가 계측이 필요하다.

## 적용 범위와 비적용 조건

- 적용: WebSocket 수신, 이벤트 저장, 알림 생성처럼 입력과 느린 I/O의 결합을 줄여야 하면서 유실을 허용하기 어려운 흐름.
- 비적용: 최신 값 하나만 중요해 중간 데이터를 버릴 수 있는 상태 스트림. 이 경우 coalescing이나 drop-oldest 정책이 더 적합할 수 있다.

## 다음에 확인할 질문

- 큐가 가득 차면 버리기, 차단, 호출자 실행 중 무엇이 일어나는가?
- 순서가 필요한 범위는 전체인가, 키별인가?
- worker 수와 queue 크기는 어떤 측정으로 정했는가?
- 포화가 네트워크 연결과 다른 메시지 처리에 주는 최악 영향은 얼마인가?
