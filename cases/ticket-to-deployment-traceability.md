# 업무 완료 상태는 검증된 전달 결과와 연결한다

## 문제

이슈 트래커, 브랜치, 커밋, 변경 요청, CI와 배포가 모두 있어도 서로 연결되지 않으면 작업의 요구사항, 변경 코드, 검증 결과와 실제 반영 상태를 한 번에 추적할 수 없다.

티켓을 코드 작성이나 merge 직후 완료하면 보드에는 끝난 작업으로 보이지만 실제 배포와 준비 상태 확인은 실패했을 수 있다. 반대로 이슈 트래커나 메신저 API 장애가 성공한 배포를 실패로 바꾸면 협업 도구가 제품 전달의 단일 실패점이 된다.

## 불변 조건

- 작업마다 추적 가능한 하나의 대표 키를 둔다.
- 티켓, 브랜치, 커밋과 변경 요청에서 같은 키를 사용한다.
- 완료 조건은 작업 유형별로 검증 가능한 결과로 정의한다.
- 운영 배포 작업은 merge가 아니라 배포와 readiness 검증 뒤 완료한다.
- 이슈 트래커와 알림 연동 실패는 관측하되 성공한 핵심 전달 결과를 되돌리지 않는다.
- 자동화가 어떤 리비전을 어떤 환경에 반영했는지 남긴다.

## 권장 흐름

```text
작업 정의
  → 작업 키가 포함된 브랜치와 커밋
  → 변경 요청의 배경·범위·완료 기준·검증 결과
  → CI 통과와 리뷰 승인
  → 배포
  → readiness 확인
  → 업무 상태 완료
  → 알림과 자동화 결과 기록
```

1. 티켓에는 배경, 변경 범위와 검증 가능한 완료 기준을 적는다.
2. 기능 브랜치와 커밋에 동일한 작업 키를 사용한다.
3. 변경 요청은 작업 키, 주요 변경, 테스트 결과와 리뷰 주의사항을 포함한다.
4. 검증 CI와 배포 CD를 분리해 리뷰 중인 코드가 운영 환경을 바꾸지 않게 한다.
5. 배포 pipeline은 merge된 변경의 작업 키와 리비전을 읽는다.
6. 배포와 readiness 확인이 성공한 뒤 운영 Task를 완료한다.
7. 이슈 트래커 또는 알림 갱신이 실패하면 재시도 가능한 별도 결과로 기록하고 배포 성공은 유지한다.

## 작업 유형별 완료 기준

| 작업 유형 | 완료 기준 예시 |
| --- | --- |
| 코드 변경 | 테스트와 리뷰가 통과한 변경이 목표 브랜치에 병합됨 |
| 운영 배포 | 목표 리비전 배포와 readiness 확인이 성공함 |
| 문서·설계 | 합의된 산출물이 리뷰·승인되고 기준 위치에 반영됨 |
| 조사·장애 분석 | 원인, 영향, 검증 결과와 남은 한계가 기록됨 |

모든 작업을 배포 성공으로 끝낼 필요는 없다. 중요한 것은 업무 유형에 맞는 완료 조건을 먼저 정하고 보드 상태가 그 결과를 반영하게 하는 것이다.

## 실패하기 쉬운 경우

### 여러 작업을 한 변경 요청에 묶음

대표 키 하나만 자동 완료하면 나머지 업무 상태가 누락되고, 모든 키를 완료하면 실제 범위가 다른 티켓까지 종료할 수 있다. 가능한 한 전달 단위로 변경 요청을 나누고, 묶어야 한다면 대표 Task와 관련 작업의 상태 전환 규칙을 명시한다.

### 키 형식만 맞고 완료 기준이 없음

연결성은 생기지만 무엇을 검증해야 끝나는지 알 수 없다. 작업 키 검사는 완료 기준과 테스트 결과를 대신하지 않는다.

### 협업 도구 연동을 핵심 배포 단계에 결합

이슈 트래커나 메신저 장애가 제품 배포를 중단시킨다. 핵심 전달과 부수 효과를 분리하고 실패를 재시도 큐나 명시적 경고로 남긴다.

### 문서 규칙만 있고 강제 장치가 없음

브랜치·커밋·변경 요청의 키 누락은 CI lint로, 리뷰 승인과 직접 push 제한은 저장소 보호 규칙으로 보완한다. 긴급 수정은 규칙을 생략하는 것이 아니라 별도 예외 절차와 사후 연결을 둔다.

## 검증 체크리스트

- 티켓부터 배포 리비전까지 같은 작업 키로 추적되는가
- 변경 요청에 배경, 범위, 완료 기준과 테스트 결과가 있는가
- 리뷰 CI와 운영 CD가 분리되어 있는가
- 티켓 완료 시점이 해당 작업의 실제 완료 조건과 일치하는가
- 배포 대상 브랜치, 리비전과 환경이 기록되는가
- 이슈 트래커·알림 실패가 배포 성공을 덮어쓰지 않는가
- 자동화 실패를 사람이 발견하고 재처리할 수 있는가
- 여러 작업 키가 들어온 변경 요청의 처리 규칙이 있는가
