# 공개 진입점과 서비스 노출 경계를 함께 설계한다

## 맥락

한 호스트나 네트워크에 리버스 프록시, 애플리케이션, 데이터 저장소가 함께 배치된 경우다. 각 서비스를 편의상 호스트 전체에 공개하면 프록시의 TLS·인증·라우팅 정책을 우회하는 경로가 생긴다.

## 불변조건

- 인터넷에 공개되는 포트는 명시한 진입점으로 제한한다.
- 애플리케이션과 데이터 저장소는 필요한 통신 주체만 접근할 수 있다.
- 브라우저의 교차 출처 허용은 실제로 필요한 출처와 메서드에 한정한다.
- 배포 검증은 외부 진입점의 상태와 내부 서비스 준비 상태를 구분한다.

## 문제와 재현

리버스 프록시만 공개한다고 가정해도 애플리케이션 포트가 모든 인터페이스에 바인딩돼 있으면 외부에서 직접 접근할 수 있다. 데이터 저장소의 호스트 포트 매핑, 넓은 CORS 정책, 공개 상태 관리 엔드포인트도 같은 방식으로 공격 표면을 넓힌다.

호스트의 실제 리스닝 주소와 방화벽 규칙, 컨테이너 포트 매핑을 함께 확인한다. 프록시를 거친 요청과 애플리케이션 포트로 직접 보낸 요청을 비교하면 우회 경로를 검증할 수 있다.

## 대안과 결정

TLS를 종료하는 ingress만 외부에 공개하고, 애플리케이션은 loopback 또는 사설 네트워크에 둔다. 데이터 저장소는 컨테이너·클러스터 내부 네트워크에만 노출한다. 프런트엔드와 API가 같은 origin을 사용할 수 있으면 프록시로 통합해 CORS 자체를 제거한다.

별도 origin의 외부 API가 필요하면 허용 출처, 메서드, 헤더, 자격 증명 정책을 명시한다. 다중 호스트나 오케스트레이션 환경에서는 loopback 대신 private subnet, 보안 그룹, network policy로 같은 경계를 구현한다.

## 검증

- 호스트와 컨테이너의 실제 리스닝 주소·포트를 열거한다.
- 외부 네트워크에서 ingress 외의 애플리케이션·데이터 저장소 포트에 접근할 수 없는지 확인한다.
- 허용하지 않은 origin과 메서드의 브라우저 요청이 거부되는지 확인한다.
- 내부 주소의 배포 health와 외부 ingress의 TLS·라우팅 health를 각각 확인한다.
- 인증서 갱신 뒤 설정 검증과 안전한 reload 절차가 동작하는지 확인한다.

## 적용 범위와 비적용 조건

- 적용: 단일 호스트 Docker 배포, VM 기반 서비스, 리버스 프록시를 둔 소규모 시스템.
- 비적용: 외부 클라이언트가 애플리케이션에 직접 접속해야 하는 명시적 요구가 있는 서비스. 이 경우에도 직접 노출 범위와 인증 정책을 별도로 제한한다.

## 다음에 확인할 질문

- 인터넷에서 실제로 열려야 하는 포트와 origin은 무엇인가?
- ingress를 거치지 않고 애플리케이션이나 데이터 저장소에 도달할 경로가 있는가?
- CORS가 필요한 이유가 다른 origin 때문인지, 잘못된 배치 구조 때문인지 확인했는가?
- 배포 준비 상태와 외부 TLS·라우팅 상태를 각각 누가 판단하는가?
