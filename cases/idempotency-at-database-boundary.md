# 재시도 멱등성의 최종 방어는 데이터베이스 불변조건에 둔다

## 맥락

장치나 외부 클라이언트는 응답을 받지 못하면 같은 사건을 다시 보낼 수 있다. 애플리케이션이 저장 전에 기존 데이터를 조회하면 순차적인 중복은 줄일 수 있지만, 두 요청이 동시에 조회한 뒤 모두 저장하는 경쟁까지 막지는 못한다.

## 불변조건

- 같은 멱등성 키를 가진 사건은 한 번만 저장된다.
- 프로세스 재시작이나 인스턴스 증가 뒤에도 같은 조건이 유지된다.
- 중복 요청은 예상 가능한 결과로 처리되고 원본 저장을 훼손하지 않는다.

## 실패하기 쉬운 접근

메모리 집합이나 짧은 시간 창은 빠르지만 프로세스 재시작과 다중 인스턴스에서 상태를 공유하지 못한다. `exists` 조회 뒤 `insert`하는 코드도 두 트랜잭션이 같은 시점에 조회하면 둘 다 통과할 수 있다. 분산 락은 해결책이 될 수 있지만, 단일 관계형 데이터베이스가 이미 최종 저장소라면 운영 복잡성이 먼저 늘어날 수 있다.

## 결정

애플리케이션 선조회는 불필요한 쓰기를 줄이는 최적화로 사용하고, 정확성은 멱등성 키의 `UNIQUE` 제약으로 보장한다. 저장 시 제약 위반은 시스템 오류와 구분해 이미 처리된 요청으로 해석한다.

키가 없는 구형 요청을 시간 창이나 복합 값으로 보조 처리할 수는 있지만, 이는 재시작·다중 인스턴스에서도 같은 보장을 제공하지 않는다. 강한 멱등성이 필요한 흐름이라면 키 발급 계약부터 고정해야 한다.

## 확인한 범위와 남은 검증

- 애플리케이션의 선조회, 즉시 쓰기, 제약 위반 처리 경로를 확인했다.
- 데이터베이스 스키마에 멱등성 키의 유일성 제약이 적용된 것을 확인했다.
- 순차 중복 요청이 한 건으로 처리되는 경로를 확인했다.
- 동일 키를 두 트랜잭션에서 동시에 저장하는 실제 데이터베이스 통합 테스트는 별도 검증이 필요하다.

## 적용 범위와 비적용 조건

- 적용: 이벤트 수집, 결제 요청, 웹훅 수신처럼 재전송될 수 있고 영속 저장이 기준인 흐름.
- 비적용: 중복을 허용하는 텔레메트리나 멱등성 키를 정의할 수 없는 임시 데이터. 이 경우 별도의 중복 허용 정책과 보관 기준이 필요하다.
