# 현재 상태는 하나의 재시작 진입점이 소유한다

## 맥락

장기 프로젝트에서는 날짜별 진행 기록, 설계 결정, 장애 기록, 운영 절차와 면접용 요약이 함께 늘어난다. 재개할 때마다 새 상태 요약을 덧붙이면 어느 절이 현재인지 알기 어려워지고, 파생 문서가 원본보다 강한 검증 상태를 주장하기 쉽다.

## 불변조건

- 현재 상태와 다음 작업은 하나의 재시작 진입점만 소유한다.
- 과거 재개 메모는 현재 상태와 분리된 이력이다.
- 결정, 관찰된 장애, 반복 절차와 날짜별 변화는 역할별 원본에 둔다.
- 파생 문서는 원본보다 강한 구현·검증 상태를 주장하지 않는다.
- 문서 링크, 안정 ID와 실제 Git 루트는 서로 다른 검사 대상으로 다룬다.

## 문제와 확인

한 프로젝트에서 재시작 절이 일곱 개까지 늘어나 날짜순도 아닌 상태로 섞였다. 각 절은 작성 당시에는 맞았지만, 시간이 지나자 과거 스냅샷과 현재 상태를 구분하기 어려웠다. 같은 사실을 여러 문서에 복사하면 한쪽만 갱신되어 상태도 어긋났다.

상대 링크가 모두 열린다고 문서 구조가 일관된 것도 아니었다. 별도 검사에서는 여러 문서가 같은 안정 ID를 다시 사용한 것을 찾았다. Git 명령을 워크스페이스 상위 폴더에서 실행하면 실제 하위 저장소의 상태를 확인하지 못하는 경계도 있었다.

## 대안과 결정

날짜가 붙은 상태 요약을 계속 추가하는 방식은 쓰기 쉽지만, 읽는 사람이 최신 절을 다시 판별해야 한다. 모든 내용을 한 문서에 모으면 검색은 단순해져도 결정 근거와 장애 이력이 현재 상태를 가린다.

현재 상태를 소유하는 진입점은 하나만 유지한다. 새 재개 메모를 쓸 때 그 절을 고쳐 쓰고, 이전 내용은 과거 기록으로 내린다. 결정은 결정 문서, 실제로 관찰한 실패는 장애 문서, 반복 명령은 절차 문서, 날짜별 결과는 일일 기록에 둔다. 면접 요약과 플레이북은 이 원본을 링크하거나 짧게 요약하되 검증 수준을 높이지 않는다.

## 검증

- 처음 보는 사람이 진입점 한 곳에서 현재 상태와 다음 작업을 찾을 수 있는지 확인한다.
- 현재 상태를 주장하는 제목이나 절이 둘 이상인지 검색한다.
- 로컬 Markdown 상대 링크가 실제 파일과 제목으로 해석되는지 검사한다.
- 결정·장애 같은 안정 ID가 중복되지 않는지 별도로 검사한다.
- Git 상태와 이력을 확인하기 전에 실제 저장소 루트를 찾는다.
- 구현, 테스트, 운영 확인과 제안 상태가 파생 문서에서 섞이지 않았는지 표본 대조한다.

이 검사는 문서 구조와 검색 가능성을 확인한다. 문서에 적힌 제품 동작이 현재 코드나 운영 환경과 같은지는 코드, 테스트와 운영 증거로 다시 확인해야 한다.

## 적용 범위와 비적용 조건

- 적용: 여러 달 이어지고 결정·장애·운영 기록이 누적되는 프로젝트.
- 비적용: 상태 변화가 적고 README 한 장으로 충분한 단기 작업. 문서를 먼저 나누면 유지 비용만 늘 수 있다.
