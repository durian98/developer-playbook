# 마이그레이션 순서와 적용 파일의 불변성을 배포 전에 확인한다

## 맥락

여러 개발자가 같은 배포 브랜치에 데이터베이스 마이그레이션을 추가하고, CI는 주로 빈 데이터베이스에 전체 마이그레이션을 처음부터 적용하는 환경이다. 파일 이름의 버전과 파일 내용은 애플리케이션 코드보다 오래 살아 있는 운영 DB 이력의 일부가 된다.

## 불변조건

- 새 마이그레이션 버전은 실제 대상 브랜치 tip에 있는 최대 버전보다 크다.
- 이미 운영 DB에 적용된 파일의 이름과 내용은 바꾸지 않는다.
- CI는 MR을 만든 시점의 기준점이 아니라 검증 시점의 대상 브랜치 tip을 기준으로 비교한다.
- 빈 DB에서 통과한 결과와 이미 사용 중인 DB에서의 순서·체크섬 검증을 같은 것으로 말하지 않는다.

## 문제와 재현

팀원이 각자 작업을 시작한 시점의 마지막 번호만 보고 파일을 만들면, 먼저 머지된 다른 마이그레이션보다 낮은 버전이 뒤늦게 들어올 수 있다. 빈 DB에서는 자연스러운 순서로 모두 적용되므로 CI가 초록이지만, 운영 DB에는 이미 더 높은 버전이 적용되어 Flyway가 out-of-order 이력을 거부한다.

적용된 파일을 나중에 이름만 올리거나 주석만 고쳐도 checksum이 바뀐다. DDL이 같다는 이유로 안전하다고 보면 이미 적용된 이력과 현재 파일의 불일치로 기동이 막힌다.

## 대안과 결정

날짜·시각을 각자 지어내는 규칙은 동시 개발과 병합 순서를 보장하지 않는다. 적용된 파일을 수정해 맞추는 방식은 운영 DB의 이력을 훼손한다.

새 파일은 검증 시점의 대상 브랜치에 있는 마지막 버전보다 크게 만든다. 이미 적용된 파일은 이름·내용을 그대로 두고, 변경이 필요하면 새 마이그레이션으로 표현한다. CI는 전체 Git history를 받아 대상 브랜치 tip과 새 파일을 비교하고, 역행·중복 가능성을 머지 전에 실패시킨다. 이 검사는 빈 DB의 애플리케이션 빌드 검사를 대체하는 것이 아니라 그 빈틈을 보완한다.

## 검증

- 대상 tip보다 낮거나 같은 새 버전이 실패하는지 확인한다.
- 적용된 파일을 수정했을 때 checksum 검증이 별도 실패하는지 확인한다.
- MR 생성 이후 더 높은 버전이 대상 브랜치에 들어온 경우에도 현재 tip 기준으로 다시 잡는지 확인한다.
- 빈 DB 전체 적용, 기존 DB validate, 실제 애플리케이션 기동을 각각 구분해 기록한다.
- 운영에서 실패했다면 health 응답뿐 아니라 실제 API가 컨트롤러까지 도달하는지 확인한다.

실제 운영에서 순서 역행과 같은 파일의 중복 수정으로 기동 실패가 반복되었고, 이후 대상 브랜치의 현재 tip과 비교하는 CI 검사를 추가했다. 새 DB 빌드가 통과했다는 사실만으로 운영 DB의 Flyway 이력을 검증했다고 말하지 않는다.

## 적용 범위와 비적용 조건

- 적용: 버전 기반 마이그레이션 도구를 여러 브랜치에서 병렬 작성·병합하는 서비스.
- 비적용: 운영 DB에 버전 파일을 사용하지 않는 무상태 배포. 그래도 스키마 변경의 순서·호환성·롤백 규칙은 필요하다.
