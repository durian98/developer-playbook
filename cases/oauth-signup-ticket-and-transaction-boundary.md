# 소셜 가입 단계는 서버 보관 1회용 티켓으로 잇는다

## 맥락

외부 신원 확인은 끝났지만 서비스 계정 생성에 필요한 닉네임·약관·연령 확인을 다음 화면에서 받아야 하는 가입 흐름이다. 인증 요청과 가입 요청을 한 번에 묶으면 사용자가 provider 화면을 통과하기 전에 서비스 약관을 처리해야 하고, 클라이언트에 외부 프로필이나 access token을 맡기면 다음 요청의 신뢰 경계가 약해진다.

## 불변조건

- 외부 인증이 끝났다고 계정을 바로 만들지 않는다.
- 다음 요청에는 서버가 확인한 provider 신원과 미리 채울 값만 이어지고, 클라이언트가 되돌려 보낸 프로필을 신뢰하지 않는다.
- 티켓은 짧은 TTL과 1회 소비를 가지며 원문은 저장하지 않는다.
- 가입·기존 계정 연결·실패 재시도의 결과가 트랜잭션 경계와 모순되지 않는다.

## 문제와 재현

처음 보는 외부 신원을 바로 계정으로 만들면 약관·닉네임·연령 확인의 시점이 어긋난다. 반대로 기존 이메일 계정과 자동 연결하면 provider별 이메일 검증 수준 차이 때문에 계정 탈취 경로가 될 수 있다.

연결이 필요하다는 결과를 예외로 던지면서 같은 트랜잭션 안에서 연결 티켓을 먼저 저장하면, 예외 처리 시 티켓 INSERT까지 롤백된다. 클라이언트는 티켓을 받았다고 생각하지만 다음 요청에서는 존재하지 않는 티켓이 된다.

## 대안과 결정

provider 프로필을 클라이언트에 넘겨 다시 받는 방식은 값을 위조할 수 있다. provider access token을 저장하는 방식은 서비스가 필요 이상으로 비밀을 보관하게 만든다. 이메일이 같다는 이유만으로 자동 연결하는 방식은 provider별 검증 차이를 없애지 못한다.

서버가 외부 신원·미리 채울 값·만료 시각을 1회용 가입 또는 연결 티켓으로 보관하고, 클라이언트에는 난수 열쇠만 준다. 데이터베이스에는 난수의 해시만 저장하고 소비 시 행을 잠근다. 화면은 `LOGGED_IN`, `SIGNUP_REQUIRED`, `LINK_REQUIRED`처럼 결과 상태로 분기한다.

티켓 발급이 성공해야 하는 정상적인 분기를 예외로 표현하지 않는다. 예외는 실패를 롤백해야 할 때 사용하고, 연결 필요처럼 티켓을 남긴 뒤 다음 단계로 넘어가는 결과는 반환값으로 표현한다. 잘못된 비밀번호처럼 연결 실패는 티켓 소비도 함께 되돌려 재시도할 수 있게 한다.

## 검증

- 외부 인증 직후 계정·신원이 생기지 않고 티켓만 생기는지 확인한다.
- 데이터베이스에서 티켓 원문을 검색해도 나오지 않는지 확인한다.
- 같은 티켓의 두 번째 사용, 만료 티켓, 없는 티켓이 모두 거절되는지 확인한다.
- 기존 계정 연결에서 잘못된 비밀번호는 연결하지 않고, 올바른 재시도는 같은 티켓으로 성공하는지 확인한다.
- 외부 provider 왕복, 실제 브라우저 cookie, 모바일 deep link는 별도 검증으로 남긴다.

실제 PostgreSQL 통합 테스트에서 티켓만 남고 계정은 생기지 않는 흐름, 해시 저장, 1회 소비, 만료·미존재 동일 응답, 기존 계정 연결, 이메일 없는 provider 가입을 확인했다. provider 네트워크 왕복과 운영 배포는 이 사례의 검증 범위가 아니다.

## 적용 범위와 비적용 조건

- 적용: 외부 인증 뒤 추가 동의·프로필 입력·계정 연결 단계가 필요한 흐름.
- 비적용: 서비스 계정이 이미 존재하고 외부 인증 결과가 곧 세션 발급으로 충분한 로그인 전용 흐름.
- 이메일이 없는 provider를 허용할지는 제품 정책이다. 허용하면 메일 기반 복구와 중복 계정의 한계를 사용자에게 알려야 한다.

## 다음에 확인할 질문

- 정상적인 중간 상태를 예외로 표현해 티켓이나 감사 기록을 롤백시키고 있지 않은가?
