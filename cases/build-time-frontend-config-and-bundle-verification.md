# 정적 프런트 설정은 번들 생성 시 주입하고 결과를 검사한다

## 맥락

정적 웹 프런트가 빌드 단계에서 환경변수를 코드에 치환한 뒤 컨테이너로 서비스되는 배포다. 실행 중인 컨테이너에 환경변수를 추가하는 것과 번들에 설정을 넣는 것은 서로 다른 시점의 동작이다.

## 불변조건

- 각 설정값이 빌드 시점과 실행 시점 중 언제 해석되는지 알고 있어야 한다.
- 빌드 시점 값은 export 전에 주입되어야 한다.
- 배포 번들에 개발 주소, `undefined`, 누락된 공개 설정이 남지 않는다.
- API 주소·콜백 주소·provider 공개 식별자가 서버 설정과 같은 환경을 가리킨다.

## 문제와 재현

빌드 단계에서 설정을 읽어 문자열로 넣는 프레임워크는 컨테이너 실행 시의 `-e`만으로 이미 만들어진 JavaScript를 바꾸지 않는다. 서버 API를 `curl`로 확인해도, 배포된 화면이 빈 provider ID나 로컬 API 주소를 들고 있으면 사용자는 로그인할 수 없다.

가장 작은 재현은 설정 없이 정적 번들을 만든 뒤 결과에서 `localhost`·`undefined`·필수 설정 누락을 찾는 것이다. 실행 시 환경변수를 추가해도 번들이 그대로라면 주입 시점이 잘못된 것이다.

## 대안과 결정

실행 시 설정 파일을 요청하는 런타임 구성은 재빌드 없이 환경을 바꿀 수 있지만, 정적 호스팅 경로·캐시·설정 파일의 공개 범위를 함께 설계해야 한다. 현재 구조에서는 Docker build argument를 export 단계까지 전달하고, 공개되어도 되는 식별자와 비밀 서버 자격증명을 구분한다.

배포 검증은 API 호출만으로 끝내지 않고 최종 번들을 직접 검사한다. 공개 설정은 값의 존재·형식을 확인하되 실제 비밀값을 로그나 문서에 남기지 않는다.

## 검증

- 시험값으로 로컬 export를 실행해 모든 필수 공개 설정이 번들에 들어가는지 확인한다.
- 번들에서 `localhost`, `void 0`, `undefined` 같은 기본값이 0건인지 확인한다.
- 머지 후 자동 배포된 최종 번들을 다시 내려받아 같은 검사를 반복한다.
- 서버가 허용하는 콜백 주소와 프런트가 보내는 주소가 문자열까지 같은지 확인한다.
- 실제 provider 왕복과 브라우저 라우트 착지는 번들 검사와 별도 단계로 확인한다.

설정 누락으로 배포 화면의 provider ID가 비어 있고 API 기본 주소가 로컬 주소로 남은 사례를 실제 최종 번들에서 확인했다. build 단계에 값을 전달한 뒤 로컬 export와 배포 번들에서 필수 값의 존재 및 개발 기본값 0건을 검증했다.

## 적용 범위와 비적용 조건

- 적용: React Native Web·SPA처럼 export/build 결과가 정적 JavaScript 번들로 고정되는 프런트.
- 비적용: 요청마다 서버 템플릿이나 런타임 설정 파일을 읽는 SSR 또는 명시적 runtime config 구조. 이 경우에도 설정 노출 경계는 검증해야 한다.
