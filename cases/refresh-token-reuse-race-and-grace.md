# refresh token 경쟁 재시도와 재사용 공격을 구분한다

## 맥락

refresh token rotation을 적용하면 한 token은 한 번만 사용되어야 한다. 하지만 브라우저 탭, 쿠키 경로, 앱 재개 같은 정상 요청이 거의 동시에 갱신을 시도하면 같은 이전 token이 경쟁적으로 들어올 수 있다. 모든 두 번째 요청을 탈취로 처리하면 정상 사용자를 로그아웃시킨다.

## 불변조건

- 오래된 token의 늦은 재사용은 token family 폐기와 인증 실패로 처리한다.
- 짧은 시간 안의 경쟁 재시도는 정상적인 동시 갱신으로 구분할 수 있다.
- grace window가 세션 폐기를 되살리거나 이미 폐기된 세션을 복구하지 않는다.
- token 원문을 재저장하거나 그대로 돌려주는 방식에 의존하지 않는다.

## 문제와 재현

rotation 직후의 응답 손실이나 두 클라이언트의 동시 갱신은 “이미 사용된 token”이라는 같은 모양을 만든다. 재사용을 즉시 탈취로 해석하면 실제 탈취와 정상 경쟁을 구분하지 못하고, 사용자가 특정 화면을 열 때마다 로그아웃되는 현상으로 나타날 수 있다.

반대로 모든 재사용을 grace로 허용하면 도난 token을 오래 살릴 수 있다. 유예 시간과 세션 상태를 함께 보지 않으면 보안 완화가 된다.

## 대안과 결정

즉시 family를 폐기하는 정책은 탈취 대응은 단순하지만 정상 경쟁에 취약하다. 같은 token을 무기한 다시 허용하는 정책은 사용자 편의는 높지만 rotation의 의미를 잃는다.

사용된 시각을 기록하고 짧은 grace window를 둔다. 유예 안의 재시도는 세션을 폐기하지 않고 새 token 쌍을 발급한다. 유예가 지났거나 세션이 이미 폐기·비활성 상태면 기존처럼 family를 폐기하고 실패시킨다. grace는 경쟁을 흡수하는 장치이지 죽은 세션을 되살리는 장치가 아니다.

## 검증

- 정상 token은 rotation되고 이전 token은 다시 정상 사용되지 않는지 확인한다.
- 유예 안의 근접 재시도는 세션을 폐기하지 않는지 확인한다.
- 유예가 0이면 기존의 즉시 폐기 동작으로 돌아가는지 확인한다.
- 유예 안이라도 이미 폐기된 세션은 되살아나지 않는지 확인한다.
- 유예 시간 선택 근거와 재사용 탐지 로그를 별도로 관측한다.

실제 운영 로그에서 정상 경쟁이 재사용 공격과 같은 오류로 나타난 사례를 확인했고, 사용 시각·유예·세션 상태를 분리한 단위 테스트를 추가했다. 다중 인스턴스의 실제 동시 트래픽과 유예 시간의 운영 최적값은 별도 부하 검증이 필요하다.

## 적용 범위와 비적용 조건

- 적용: rotation을 사용하고 하나의 세션이 여러 클라이언트 경로에서 갱신될 수 있는 인증 시스템.
- 비적용: token rotation을 사용하지 않는 단순 bearer 세션. 이 경우 재사용 판정 자체가 다른 문제다.
- grace가 길어질수록 탈취 탐지 지연이 커지므로 사용자 경험만으로 값을 정하지 않는다.
