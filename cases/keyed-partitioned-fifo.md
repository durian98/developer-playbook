# 순서 보장 범위를 key 단위로 줄여 병렬성을 얻는다

## 맥락

같은 대상의 작업은 도착 순서대로 처리해야 하지만, 서로 다른 대상까지 전역 순서로 묶을 필요는 없는 비동기 처리다. 전역 단일 worker는 순서를 지키기 쉽지만 독립적인 작업까지 직렬화한다. 반대로 공유 큐의 worker 수만 늘리면 같은 대상의 완료 순서가 바뀔 수 있다.

## 불변조건

- 같은 key 안의 작업은 제출 순서와 완료 순서를 유지한다.
- 서로 다른 key는 서로 기다리지 않고 병렬 처리할 수 있다.
- 파티션과 큐의 상한, 포화 시 동작, hot key의 영향을 관측할 수 있다.

## 문제와 재현

전역 worker를 늘리는 방식은 처리량을 높일 수 있지만 같은 key의 작업이 서로 다른 worker에서 끝나 순서가 뒤집힐 수 있다. 전역 단일 worker를 유지하면 순서는 보장되지만 한 key의 지연이 모든 key로 전파되는 head-of-line blocking이 생긴다.

key가 있는 합성 작업을 여러 파티션에 흘려보내고, 같은 key의 완료 순서·누락·실패·파티션별 처리량을 함께 기록하면 두 문제를 재현할 수 있다.

## 대안과 결정

전역 단일 worker는 구현이 단순하지만 독립 작업의 병렬성을 버린다. 공유 큐의 다중 worker는 구조가 간단하지만 key별 순서를 별도로 보장해야 한다. 브로커의 partition 기능은 확장 선택지가 될 수 있지만 운영 요소와 재분배 정책이 먼저 필요하다.

업무상 필요한 순서가 전역이 아니라 key별이라면 key를 고정된 파티션에 해시하고, 각 파티션에는 한 번에 하나의 consumer만 둔다. 파티션 사이만 병렬화한다. 큐를 무제한으로 만들지 않고, 포화 시 차단·호출자 실행·거부·유실 중 어떤 동작을 선택했는지도 함께 기록한다.

## 검증

- 로컬 A/B에서 전역 단일 worker와 key 파티션을 같은 입력으로 비교한다.
- 각 key의 완료 순서가 세 번의 반복에서 모두 지켜지는지 확인한다.
- 처리량과 p99뿐 아니라 누락·실패·순서 위반을 함께 센다.
- 파티션 수를 늘렸을 때 DB pool, 외부 호출량, hot partition이 새 병목이 되지 않는지 확인한다.

합성 부하에서 4개 파티션은 전역 단일 worker보다 중앙 처리량을 약 3.4배 높이고 p99를 약 70% 줄였으며, 저장 누락·실패·key별 순서 위반은 없었다. 이는 로컬 단일 애플리케이션과 합성 작업의 결과이지 운영 수치나 다중 인스턴스 보장은 아니다.

## 적용 범위와 비적용 조건

- 적용: 사용자·장치·주문처럼 key별 순서가 중요하고 서로 다른 key는 독립적인 비동기 처리.
- 비적용: 모든 key 사이의 전역 순서가 업무 불변조건인 경우. 이때 파티션 분할은 요구사항을 깨뜨린다.
- 비적용: key 분포가 극단적으로 한쪽에 몰리고 hot key를 분리하거나 제한할 방법이 없는 경우.

## 다음에 확인할 질문

- 정말 필요한 순서는 전역인가, key별인가?
- key가 편향될 때 가장 느린 파티션의 큐 길이와 p99는 얼마인가?
- 파티션 수를 늘린 비용이 DB pool과 외부 시스템의 한도를 넘지 않는가?
